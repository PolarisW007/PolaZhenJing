# 需求记录:文章编辑页保存 413 修复

日期:2026-06-09

## 原始需求

2026-06-09 00:46 线上反馈:在 `https://aipd.me/PolaZhenjing/admin/articles/rolling-ai-fde-ai-20260607.md/edit` 提交保存时,浏览器返回「Request Entity Too Large / The data value transmitted exceeds the capacity limit.」文章 markdown 源仅 8KB,但在 TinyMCE 富文本模式下保存即失败。

## 目标

- 让文章编辑页在富文本模式下保存正常长文(8KB markdown 转 HTML 后 500KB+)不再 413。
- 维持编辑页与上传页同款 TinyMCE 双模式编辑器,不动用户可见行为。
- 修复部署后,`rolling-ai-fde-ai-20260607.md` 等已发布文章可以正常再编辑保存。

## 非目标

- 不重写编辑页交互(模式切换、按钮、预览)。
- 不替换 Werkzeug 或调整 gunicorn 启动参数。
- 不动 nginx(已设 `client_max_body_size 16m`,远超本次所需)。
- 不重写 TinyMCE HTML 序列化逻辑(避免引入更多风险)。
- 不拆分 `body` 字段为 multipart 上传(过度设计,本轮 16MB 单字段足够)。
- 不做 `MAX_CONTENT_LENGTH` / `MAX_FORM_MEMORY_SIZE` 之外的额外大小保护(留给后续按需加)。

## 验收标准

- A1 文档:需求 / PRD / devlog / test-report / release 5 份交付物覆盖本次修复。
- A2 后端:`app/__init__.py` 新增 `app.config['MAX_FORM_MEMORY_SIZE'] = 16 * 1024 * 1024`,和 `MAX_CONTENT_LENGTH` 对齐。
- A3 前端:`article_edit.html` 提交流程把 `content` 和 `rich_content` 两个 textarea `disabled = true`,避免同篇正文在 form 里出现 3 份。
- A4 单测:新增 `tests/test_article_edit_413_fix.py`,500KB / 1MB / 8MB body 都不再 413,302 跳回详情页。
- A5 全部测试通过:本地 + 云端 `pytest tests` 34/37 passed。
- A6 云端 `polazj.service` 重启后端到端:8KB / 100KB / 500KB / 1MB body 走 nginx → gunicorn 全部 302。
- A7 不破坏既有功能:本次改动只动 `app/__init__.py` 和 `app/templates/article_edit.html`,其它路由、TinyMCE 加载、图片上传、revision_instruction 流程均不变。
- A8 已发布文章可正常再编辑:云端 `rolling-ai-fde-ai-20260607.md` 等大文章加载与保存均正常。

## 风险

- R1 `MAX_FORM_MEMORY_SIZE` 提到 16MB 后,DoS 攻击面扩大;但本接口受 `@login_required` 保护,且只暴露给 admin 角色(实际只有你一个人),风险可控。
- R2 前端 `disabled` 只在 submit 事件中设置,极端竞态(JS 注入)可能让 `content` / `rich_content` 重新 enabled 后被发送;但 `body` 已经是 canonical 字段,后端只读 `body`,即便其他两份也被发送,Werkzeug 也会以 body 大小为标准判断。
- R3 修复后,云端 1MB+ 的大 body 首次保存时,反向代理 + gunicorn + 文件 IO 链路会稍微变慢;按当前 1MB 大小评估,延迟增加 < 200ms,可接受。
- R4 后续若支持「附件上传」或「嵌入 PDF」,单字段会进一步膨胀,届时需要重新评估限制;本轮不预先优化。
