# 开发日志:文章编辑页保存 413 修复

日期:2026-06-09

## 目标

修掉 2026-06-09 00:46 线上反馈:文章编辑页富文本模式保存时浏览器显示「Request Entity Too Large」。同时补齐需求 / PRD / 测试报告 / 发布记录 5 份交付物。

## 排查记录

- 抓 Werkzeug 3.1.8 源码(`venv/lib/python3.14/site-packages/werkzeug/formparser.py`),确认 `max_form_memory_size` 默认 500000 字节(500KB),超过直接 `raise RequestEntityTooLarge`。
- 用 `app.test_client()` 逐步放大 body 跑 POST,500KB / 1MB / 5MB / 16MB / 17MB 全部 413,500KB 之前全 302。
- 直接看 `app/__init__.py:148` `MAX_CONTENT_LENGTH = 16MB` 早已存在但被 Werkzeug 先拦,无效;nginx `client_max_body_size 16m` 也未触发。
- 二次根因:前端 `article_edit.html` 提交时 form 同时有 `body` + `content` + `rich_content` 三个字段,富文本 HTML 1.5-2x 膨胀,合计 size 经常触碰 500KB 边界。

## 改动记录

- `app/__init__.py`
  - 新增 `app.config['MAX_FORM_MEMORY_SIZE'] = 16 * 1024 * 1024`,和 `MAX_CONTENT_LENGTH` 对齐。
- `app/templates/article_edit.html`
  - 提交事件处理中,`tinymce.triggerSave()` 之后设置隐藏 `body` 字段前后,加 `markdown.disabled = true` 和 `rich.disabled = true`,避免同篇正文在 form 里出现 3 份。
- `tests/test_article_edit_413_fix.py`(新增)
  - 用 `tmp_path` 隔离 `_posts/`,3 个用例:500KB / 1MB / 8MB body 都不再 413,302 跳详情页。

## 风险

- R1 `MAX_FORM_MEMORY_SIZE` 提到 16MB 后,DoS 攻击面扩大;但本接口受 `@login_required` 保护,只暴露给 admin 角色,实际只有你一个人用,风险可控。
- R2 修复后云端 1MB+ 大 body 首次保存链路延迟略增(< 200ms 经验值),可接受。
- R3 后续若支持「附件上传」或「嵌入 PDF」,单字段会进一步膨胀,届时需要重新评估限制;本轮不预先优化。
