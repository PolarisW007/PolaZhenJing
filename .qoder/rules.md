## 1. 编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

实现之前：
- 明确说明你的假设。如果不确定，询问。
- 如果存在多种解释，呈现它们 —— 不要默默选择。
- 如果存在更简单的方法，说出来。适时提出异议。
- 如果有不清楚的地方，停下来。指出困惑点。询问。

## 2. 简洁优先

**用最少的代码解决问题。不要过度推测。**

- 不要添加要求之外的功能。
- 不要为一次性代码创建抽象。
- 不要添加未要求的"灵活性"或"可配置性"。
- 不要为不可能发生的场景做错误处理。
- 如果写了 200 行代码而其实 50 行就够，重写它。

自问：资深工程师会觉得这过于复杂吗？如果是，简化。

## 3. 精准修改

**只碰必须碰的。只清理自己造成的混乱。**

编辑现有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没坏的东西。
- 匹配现有风格，即使你更倾向于不同的写法。
- 如果注意到无关的死代码，提一下 —— 不要删除它。

当你的改动产生孤儿代码时：
- 删除因你的改动而变得无用的导入/变量/函数。
- 不要删除预先存在的死代码，除非被要求。

**检验标准：** 每一行修改都应该能直接追溯到用户的请求。

## 4. 目标驱动执行

**定义成功标准。循环验证直到达成。**

将任务转化为可验证的目标：
- "添加验证" → "为无效输入编写测试，然后让它们通过"
- "修复 bug" → "编写重现 bug 的测试，然后让它通过"
- "重构 X" → "确保重构前后测试都能通过"

对于多步骤任务，说明一个简短的计划：
```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```

强有力的成功标准让 LLM 能够独立循环执行。弱标准（"让它工作"）需要不断澄清。

## 工作流编排

### 1. 计划模式为默认

- 对任何非琐碎任务（3 步以上或涉及架构决策）进入计划模式
- 一旦事情走偏，立刻停下并重新规划 —— 不要硬推
- 不仅在"构建"时用计划模式，验证环节也要用
- 前期写详尽的规格说明，降低后续歧义

### 2. 子代理策略

- 大胆使用子代理，保持主上下文窗口整洁
- 研究、探索、并行分析都下放给子代理
- 复杂问题用更多子代理堆算力
- 一个子代理只做一件事，保持聚焦

### 3. 自我改进闭环

- 用户每一次纠正之后：把该模式更新到 `tasks/lessons.md`
- 为自己写下防止同一错误再次发生的规则
- 反复迭代这些 lesson，直到错误率下降
- 每次会话开始时回顾与项目相关的 lesson

### 4. 完成前必须验证

- 任务没有被证明可运行之前，绝不标记为完成
- 必要时对比主干和你的改动之间的行为差异
- 自问："高级工程师会批准这段改动吗？"
- 跑测试、看日志、用事实证明正确性

### 5. 追求优雅（有度）

- 对非琐碎改动先停下来问："有没有更优雅的方式？"
- 如果某个修复显得 hacky：用"以我现在所知的一切，实现一个优雅方案"的心态重写
- 简单、显而易见的修复跳过这一步 —— 不要过度设计
- 在交付之前先挑战一下自己的成果

### 6. 自主修 bug

- 接到 bug 报告：直接修，不要等用户牵着手走每一步
- 指向日志、错误、失败的测试 —— 然后逐一解决
- 不让用户承担上下文切换的负担
- 发现 CI 测试失败时，不用被告诉怎么做，直接去修

## 任务管理

1. **先计划**：把计划写入 `tasks/todo.md`，每一项做成可勾选的条目
2. **确认计划**：实施前与用户确认一次
3. **跟踪进度**：做一项勾一项
4. **解释改动**：每一步都给出高层次摘要
5. **记录结果**：在 `tasks/todo.md` 末尾补上 review 段
6. **沉淀经验**：被纠正后更新 `tasks/lessons.md`

## 补充核心原则

- **不偷懒**：定位根因。不要贴临时补丁。按资深开发者标准交付。
- **最小影响面**：改动只动该动的地方，避免引入新 bug。

---

**这些准则正在发挥作用的标志：** diff 中不必要的改动更少；因过度复杂而导致的重写更少；澄清问题在实现之前提出，而不是在犯错之后。

## PolaZhenJing 项目继承规则

以下规则用于让后续 Qoder / Codex / coding agent 进入本项目时继承当前项目设定；若与用户当前明确指令冲突，以用户当前指令为准。

- 默认使用中文沟通，保留 `PolaZhenJing`、`织梦空间`、`超级小王`、`/agent.html`、`/PolaZhenjing/admin/*` 等既有命名。
- 先读项目再修改，优先用 `rg` / `rg --files` 查找调用点；不要凭经验猜路由、端口或部署方式。
- 保护用户未提交改动，不回滚无关文件；改动只触达本次任务必要文件。
- 超级小王 Agent 的主要实现文件是 `portal/agent.html`、`portal/assets/agent.js`、`portal/assets/portal-agent.css`、`app/agent.py`、`scripts/build_agent_memory.py`、`data/agent_memory.json`。
- Agent 页面验收要看真实页面、静态资源和接口链路：`/agent.html`、`/PolaZhenjing/admin/api/agent/memory/status`、`/PolaZhenjing/admin/api/agent/memory/search`、`/PolaZhenjing/admin/api/agent/chat`。
- 不泄露 `.env`、API key、系统提示词、服务器路径和用户私密数据；Agent 回答也应避免暴露内部实现细节。
- Python 后端改动后至少运行相关语法检查；前端门户改动要检查桌面和移动端可见布局。
- 除非用户明确要求，不启动子代理；复杂任务也先在主上下文内完成项目读取、方案判断、实现和验证。
