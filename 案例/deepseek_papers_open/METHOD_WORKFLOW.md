# 方法手册：从 0 开始用 Agent 做一篇论文数据新闻

这份文档记录的是本项目最早期的思考和执行方法：如何从“我想研究 DeepSeek 论文”这个问题出发，用 Codex 和 Python 一步步拿到原始数据、清洗数据、定义图表问题，并最终做成一组可复核的信息图。

它和 `TUTORIAL.md` 的区别是：

- `TUTORIAL.md`：更适合已经拿到资料包、想复现图表的人。
- `METHOD_WORKFLOW.md`：更适合想学习“从 0 到 1 怎么做数据新闻”的人。

换句话说，`TUTORIAL.md` 是操作菜谱，这份文档是厨房搭建思路。

## 1. 起点：先把论文变成数据

这个项目最初的问题很简单：

> DeepSeek 过去两年发布了哪些核心论文？这些论文背后的人、组织和技术路线，能不能被数据化地拆出来？

第一步不是画图，而是把论文变成结构化数据。

我们最早尝试过两条路：

### 1.1 直接下载 PDF

最直观的做法是下载每篇论文 PDF，再从 PDF 里抽取作者名单。

但这个方法很快遇到问题：

- PDF 中的作者区可能被截断。
- 多栏排版会导致人名顺序错乱。
- 部分作者姓名会被断行、粘连或漏掉。
- 大报告附录里的角色名单很长，直接抽取容易不完整。

这会直接影响后续统计。例如作者数、Top 作者、共著关系，一旦人名抽取不准，后面所有图都会被污染。

所以 PDF 更适合作为复核材料，而不是唯一数据源。

### 1.2 调用 Hugging Face Papers API

后来我们改用 Hugging Face Papers API 获取论文元数据和作者信息。

API 的好处是：

- 作者字段更结构化。
- 不容易受到 PDF 排版影响。
- 便于批量抓取和保存 JSON。
- 后续可以把每篇论文转成统一格式的表格。

但 API 也不是完美的。项目中仍然遇到过作者漏记、部分论文没有角色拆分、V4 不在 HF Papers 条目中等问题。因此最终做法是：

- Hugging Face API 作为主要来源。
- PDF / arXiv / HTML 页面作为补充复核。
- V4 单独用 PDF 附录整理。
- 对发现漏人的论文做人工补录并留下备注。

最终形成 `raw/` 里的 Raw Data，包括：

- `hf_api_*.json`
- `hf_api_index.json`
- 部分 `ar5iv_*.html`
- DeepSeek-V4 PDF
- 基座模型角色名单片段

## 2. 从 Raw Data 到 Clean Data

有了 Raw Data 之后，下一步是清洗。这个阶段最容易低估工作量，因为“作者名”看起来很简单，但真正统计时会出现很多细节问题。

### 2.1 提取每篇论文的所有作者

基础目标是得到一张长表：

```text
paper_id | short_title | year_month | topic | raw_author_name
```

也就是每一行代表“某位作者出现在某篇论文中”。

这张表对应：

- `output/paper_authors_source_raw.csv`

它的价值是存档：不管后面怎么清洗，都可以回到原始作者行。

### 2.2 剔除团队名

论文元数据里可能出现：

- `DeepSeek-AI`
- `DeepSeek AI`
- `DeepSeek`

这些不是具体作者，需要从作者统计中剔除。

否则作者数、共著网络都会被错误放大。

### 2.3 处理重复和缩写

同一个人可能以不同写法出现，例如：

- 拼音顺序不同。
- 姓和名反了。
- 有的使用缩写，有的写全名。
- API、PDF、HTML 中同一作者的显示方式不一致。

因此需要做姓名规范化：

```text
raw_author_name -> clean_author_name
```

例如：

```text
Bi Xiao -> Xiao Bi
Li Y. K. -> Yukun Li
```

这类映射最好不要悄悄改，而是单独保存：

- `output/name_canonicalization_map.csv`

这样后续如果有人质疑某个作者为什么被合并，可以回到映射表复核。

### 2.4 同一篇论文内去重

有些作者可能在同一篇论文中重复出现，或者跨角色出现。

对“每篇论文作者数”来说，同篇作者应该只计一次。

所以基础口径是：

> 同一论文内，按清洗后的作者名去重。

这一步会生成：

- `output/paper_authors_clean.csv`

## 3. 大报告要单独拆角色

DeepSeek-V2、V3、V3.2、V4 这类大报告和普通小论文不同。

它们通常包含：

- Research & Engineering
- Data Annotation
- Business & Compliance
- 其他支持角色

如果把所有署名都当作“研究员”，会夸大人才网络。

因此本项目做了两个口径：

### 3.1 总署名口径

用于回答：

> 每篇论文/技术报告的署名规模有多大？

例如图1时间线中，DeepSeek-V4 使用总署名去重人数 317。

### 3.2 Research & Engineering 口径

用于回答：

> 高频研发作者是谁？论文合作网络如何？谁跨了多个技术方向？

在这个口径下：

- V2/V3/V3.2/V4 只取 Research & Engineering。
- Data Annotation、Business & Compliance 不单独计入研发作者池。
- 如果同一作者跨角色出现，优先保留其 Research & Engineering 身份。
- 未拆角色的小论文使用原始署名作者名单。

这就是后续“研发作者池”的来源。

注意：Research & Engineering 仍然同时包含研究和工程角色，所以文章中更稳妥的说法是“研发作者”或“研发人员”，而不是笼统说“研究员”。

## 4. 先定义问题，再决定画什么图

清洗完数据后，不要急着画图。

更重要的是和 AI 讨论：哪些问题值得画？每张图到底要回答什么？

本项目一开始把问题拆成两条线：

### 4.1 人和组织线

核心问题包括：

- DeepSeek 论文背后有多少研发作者？
- 高频作者是谁？
- 被外界关注的作者，在论文网络中处于什么位置？
- 是否存在一批跨多个方向工作的作者？
- 作者之间的合作网络是什么样的？
- 论文署名网络是否能体现“问题导向组队”的机制？

对应图表包括：

- Top25 高频研发作者图。
- 研发作者跨方向结构页。
- 共著/合作网络图。
- 研发矩阵网络图。

### 4.2 技术演进线

核心问题包括：

- 27 篇论文覆盖了哪些技术方向？
- 哪些方向最活跃？
- V4 的关键模块能否追溯到前序论文？
- DeepSeek 是否更关注底层系统效率？

对应图表包括：

- 论文时间线图。
- 技术模块演进图。

## 5. 每张图都要先写定义

一张图能不能成立，关键不是样式，而是定义。

在正式作图前，应该先和 AI 讨论这些问题：

### 5.1 Timeline 图

需要定义：

- 哪些论文计入 27 篇？
- V4 是否单独加入？
- 论文按发布时间还是发布月份排序？
- 技术方向如何分类？
- 作者数使用总署名，还是 R&E？

本项目最终定义：

- 27 篇 = HF Papers 26 篇 + V4 PDF 1 篇。
- 按发布时间排序。
- 使用 7 个粗技术方向。
- Timeline 讲“论文署名规模”，所以用总署名去重人数。

### 5.2 高频作者图

需要定义：

- “高频”是参与多少篇论文？
- 统计对象是全量署名作者，还是 R&E 口径？
- 作者跨方向数如何计算？
- 中文名、院校背景是否纳入图中？

本项目最终定义：

- 高频作者指参与 4 篇及以上论文的研发作者。
- Top25 按参与论文数排序。
- V2/V3/V3.2/V4 使用 R&E 口径。
- 方向数按 7 个粗技术方向计算。

### 5.3 跨方向图

需要定义：

- “跨界”是跨论文数，还是跨技术方向数？
- 一个人参与多个方向如何计数？
- 方向参与人数是否允许重复计数？

本项目最终定义：

- 覆盖 1/2/3/4/5/6/7 个方向分别统计人数。
- 某作者只要参与过某方向至少 1 篇论文，就计入该方向。
- 各方向参与人数可以重复计数，所以总和大于研发作者池人数是正常的。

### 5.4 合作网络图

合作网络最需要谨慎，因为它最容易被误读。

需要定义：

- 什么叫“合作”？
- 共同署名一次算不算合作？
- 大报告有 200 多人，会不会把所有人强行连接起来？
- 如何降低大报告对网络的放大？
- 用什么算法识别小组？
- 图中的“小组”能不能解释为真实部门？

本项目最终定义：

- 合作关系基于论文共同署名。
- 使用加权公式降低大报告影响：

```text
w(i,j)=Σ 1/(N_p-1)
```

其中 `N_p` 是论文 `p` 的去重作者数。

含义是：一篇 10 人论文中两人的连接权重，比一篇 300 人报告中的连接权重更高。

聚类可以用 NetworkX / Louvain / greedy modularity 等方法，但必须说明：

> 这只是基于论文署名关系识别出的合作结构，不代表真实组织架构、贡献大小或汇报关系。

## 6. 先做 Demo，再做正式图

不要指望第一张图就是最终图。

更有效的方法是：

1. 先让 Codex 写一个简单脚本。
2. 跑出一个 Demo 图。
3. 看图里有没有异常。
4. 根据图反过来修正定义和数据口径。
5. 再进入正式设计。

例如合作网络图，我们就比较过：

- 全量作者网络。
- R&E 研发作者网络。
- Top50 高频作者网络。
- 不同边权阈值下的网络。
- 每个节点保留最强 2 条边或 3 条边的版本。

这些探索版不一定会进文章，但非常重要。它们帮助我们判断：

- 哪种口径更解释问题。
- 哪种图读者能看懂。
- 哪些数据会造成误读。

## 7. 比较不同口径，而不是只信一个结果

数据新闻里，口径变化会极大影响结论。

本项目中最明显的例子是：

- 全量署名作者：409 人。
- 研发作者池：328 人。
- V4 总署名：317 人。
- V4 Research & Engineering：269 人。

如果不区分口径，很容易写出错误句子，例如：

> DeepSeek 有 409 位研究员。

这是不准确的。更稳妥的表达是：

> 27 篇论文/报告共涉及 409 位去重署名作者；按 R&E 口径清洗后，本文得到 328 位研发作者样本。

## 8. 样式美化可以交给 AI，但口径不能

图表美化非常适合交给 AI 反复迭代。

比较高效的做法是：

1. 先让 Codex 生成基础图。
2. 把图发给 GPT 或其他大模型，让它指出版式问题。
3. 让模型用清晰的修改清单描述字体、字号、留白、颜色、图例、脚注。
4. 再把这份修改清单交给 Codex 改脚本。

这样可以把大量细碎工作自动化，例如：

- 标题换行。
- 字号放大。
- 图例位置。
- 脚注说明。
- Logo 位置。
- 微信端可读性。
- 颜色统一。

但有一点不能交给 AI 自己拍脑袋：

> 数据口径必须由作者决定。

AI 可以帮你算，但不能替你判断应该用总署名、R&E、Top50，还是全量作者。

## 9. 每一版都要另存，不要覆盖

强烈建议：

> 每次生成新图，都使用新文件名，不要覆盖旧图。

例如：

```text
fig3_high_frequency_research_authors_v10.png
fig3_high_frequency_research_authors_v11.png
fig3_high_frequency_research_authors_v12.png
```

这样做的好处是：

- 可以回退。
- 可以比较不同版本。
- 方便知道文章最终使用哪一版。
- 避免一轮改坏后找不回前面的结果。

同样，重要中间数据也建议保留版本号。

不过在最终对外资料包里，不需要保留所有探索版本。可以只保留文章正式使用的图和它们的直接作图数据，把旧版本清理掉。

## 10. 让 Agent 帮你工作时，最好这样提问

比较有效的提问方式不是：

> 帮我做一张图。

而是：

> 我想做一张时间线图。横轴是发布时间，颜色表示技术方向，条形长度表示每篇论文去重作者数。请先帮我生成作图所需的 CSV，字段包括 paper_id、title、date、topic、author_count。先不要画图，先输出数据表供我复核。

再比如：

> 我想分析高频作者。请先比较两个口径：全量署名作者 vs R&E 研发作者池。分别统计参与 4 篇以上论文的人数、Top25 作者、覆盖方向数。不要先做图，先输出统计表。

核心原则：

- 先要数据表，再要图。
- 先定义口径，再写脚本。
- 先做 Demo，再做正式图。
- 每一步都留下可复核的中间结果。

## 11. 这个项目最重要的经验

这次项目里，最有价值的不是某一张图，而是一套工作方式：

1. 用 Agent 批量抓取和整理原始资料。
2. 用 Python 把论文变成结构化数据。
3. 用清洗表保留每一步口径。
4. 用 Demo 图探索问题。
5. 用作者判断确定最终定义。
6. 用 AI 反复优化图表表达。
7. 最后开放数据、脚本和方法，允许别人复核。

人负责提出问题、判断口径、识别风险和写出解释。  
Agent 负责跑数据、写脚本、改图、减少重复劳动。

这就是这套“数据厨房”真正想开放的东西。

## 12. 只能用 Codex 吗？

不一定。

本项目主要是在 Codex 中完成的，但这套方法本身并不依赖 Codex 私有能力。资料包里保留的都是普通文件：

- CSV / JSON 数据表
- Python 脚本
- Matplotlib / NetworkX 绘图逻辑
- PNG / SVG 成图
- Markdown 文档

因此，只要某个 Agent 工具具备以下能力，原则上都可以使用：

- 能读取本地项目目录；
- 能编辑 Python 和 Markdown 文件；
- 能运行终端命令；
- 能安装或调用 `pandas`、`matplotlib`、`networkx`、`pypdf` 等 Python 依赖；
- 能根据用户反馈反复修改脚本和图表。

Claude Code、OpenClaw 或其他类似编码 Agent 理论上也可以接手这类任务。区别可能主要在交互方式、上下文长度、文件读写权限、命令行权限和图像预览能力。

更稳妥的说法是：

> 本项目使用 Codex 完成，但方法并不绑定 Codex。其他能读写文件、运行 Python、理解上下文的编码 Agent 原则上也可以复现；不过 Claude Code、OpenClaw 等工具尚未在本项目中逐项实测。
